## 1. 하드웨어 연결

| 항목 | Raspberry Pi 쪽 | POWER 보드(DSP) 쪽 |
|---|---|---|
| 장치 | `/dev/ttyAMA2` (UART3) | TMS320F2800155 SCIB |
| 핀 | TX GPIO4, RX GPIO5 | TX GPIO12, RX GPIO13, 방향 제어 GPIO20 |
| 트랜시버 | RS485 IC, **자동 방향 전환** (소프트웨어 제어 없음) | ADM3483, DE와 /RE를 묶어 GPIO20으로 제어 |

- DSP는 송신 시작 전에 DE를 5µs 먼저 켜고, 마지막 비트가 나간 뒤 3µs 더 유지한다(`DE_SETUP_US`, `DE_HOLD_US`).
- DSP에는 설정용 UART 메뉴(SCIA)가 따로 있다. Modbus(SCIB)와는 별개다.
- 2026-11-13: Pi와 PC의 RS485 변환기 사이에서 9600bps 양방향 송수신을 확인했다. 그날 RS485 IC 전원 문제가 있었으므로 **신호가 없으면 485 IC 전원부터 확인**한다.

### 배선 시험 모드

`modbus_rtu.h`의 `RS485_TEMP_A_TEST`를 1로 바꿔 빌드하면, DSP는 Modbus에 응답하지 않고 ASCII `'5'`(0x35)만 계속 보낸다.
기본값은 0이다. Pi에서 `5`가 반복 수신되면 DSP가 이 모드로 빌드된 것이다.

## 2. 통신 규격

| 항목 | 값 |
|---|---|
| 프로토콜 | Modbus RTU, Pi가 마스터 |
| 속도 | **9600 bps** |
| 데이터 형식 | **8E1** (8비트, 짝수 패리티, 정지 비트 1) — **8N1이 아님** |
| 슬레이브 주소 | **1** (고정, 다른 주소와 브로드캐스트 0에는 응답하지 않음) |
| 지원 기능 | 0x03 설정 읽기, 0x04 측정 읽기, 0x06 레지스터 하나 쓰기, 0x10 여러 레지스터 쓰기 |
| CRC | CRC-16/Modbus (초기값 0xFFFF, 다항식 0xA001), **하위 바이트 먼저** |
| 레지스터 주소 | 0부터 시작하는 PDU 주소 (40001, 30001 같은 표기는 쓰지 않음) |
| 16비트 값 | 상위 바이트 먼저 |
| float32 | IEEE 754, **ABCD 순서** (상위 word 먼저, word 안에서도 상위 바이트 먼저). Python에서는 `struct.pack('>f', v)` |

> 2026-11-13 배선 시험은 8N1로 했다. 실제 Modbus 통신은 **반드시 8E1로 열어야 한다.**
> 8N1로 보내면 DSP에서 패리티 오류가 나고, DSP는 그 프레임을 버린다.

### 타이밍

| 항목 | 값 | 근거 |
|---|---|---|
| 문자 1개 | 11비트, 약 1.146ms | 8E1 = 시작 1 + 데이터 8 + 패리티 1 + 정지 1 |
| 프레임 내부 허용 간격 (t1.5) | 1.719ms | 이보다 길게 끊기면 DSP가 프레임을 불량으로 버림 |
| 프레임 끝 판정 (t3.5) | 4.011ms | 이만큼 조용하면 DSP가 프레임 끝으로 판단 |
| **마스터 요청 간 최소 간격** | **5ms 이상** | 직전 응답 수신 완료부터 다음 요청까지 |
| 응답 제한 시간 | 100ms | 참조 클라이언트 기준 |
| FC04 전체 응답 | 37바이트, 약 42.4ms | |

- **요청 프레임은 반드시 한 번의 `write()`로 보낸다.** 바이트를 나눠 보내다가 1.719ms 이상 끊기면 DSP가 프레임을 버린다.
- DSP는 CRC 오류, 주소 불일치, 길이가 맞지 않는 프레임에는 **응답하지 않는다.** 응답이 없으면 이 경우를 의심한다.

## 3. 측정 레지스터 — FC04 (읽기 전용)

한 번에 읽는다: 시작 0, 개수 16. 응답 바이트 수 필드는 32(0x20)다.

| 주소 | 개수 | 항목 | 형식 / 단위 |
|---:|---:|---|---|
| 0~1 | 2 | 입력 전압 (DCPT1, LPF) | float32 V |
| 2~3 | 2 | 출력 전압 (DCPT2, LPF) | float32 V |
| 4~5 | 2 | 출력 전류 (DCCT2, LPF) | float32 A |
| 6 | 1 | 운전 상태 | uint16: 0=STOP, 1=RUN, 2=TRIP |
| 7 | 1 | 트립 원인 | uint16: 0=없음, 1=TIMER1 인터럽트 오류, 2=ADC 인터럽트 오류, 3=과전류(OC), 65535=알 수 없음 |
| 8 | 1 | 과전류 트립 여부 | uint16: 0=없음, 1=발생 |
| 9 | 1 | 운전 경과 시간 | uint16 초 |
| 10~11 | 2 | VBAT (LPF) | float32 V |
| 12~13 | 2 | P12V (LPF) | float32 V |
| 14~15 | 2 | RUN 중 출력 전류 최댓값 | float32 A |

- 운전 상태 0(STOP)에는 DSP가 부팅 직후 내부적으로 거치는 대기 상태(`_STANDBY`)도 포함된다.
- 전류 최댓값은 LPF 값이 아니라 RUN 중의 순간 최댓값이다. RUN을 시작할 때 0으로 초기화된다.
- 서로 다른 요청으로 읽은 값은 같은 시점의 값이 아니다. 같은 시점의 값이 필요하면 한 번에 16개를 다 읽는다.

Python으로 해석하기:
```python
data = frame[3:-2]                                   # 32바이트
vin, vout, iout = struct.unpack('>fff', data[0:12])
state, trip, oc, elapsed = struct.unpack('>HHHH', data[12:20])
vbat, p12v, peak = struct.unpack('>fff', data[20:32])
```

## 4. 설정 레지스터 — FC03 읽기, FC06·FC10 쓰기

FC03으로 한 번에 읽는다: 시작 0, 개수 8. 응답 바이트 수 필드는 16(0x10)이다.

| 주소 | 개수 | 항목 | 형식 / 허용 범위 | 쓰기 방법 |
|---:|---:|---|---|---|
| 0~1 | 2 | 출력 전압 지령 | float32, 1~300 V | FC10 |
| 2~3 | 2 | 출력 전류 지령 | float32, 0.1~1 A | FC10 |
| 4~5 | 2 | 과전류(OC) 임계값 | float32, 0.3~1.5 A | FC10 |
| 6 | 1 | 운전 제한 시간 | uint16, 1~9999 초 | FC06, 또는 FC10으로 한 번에 |
| 7 | 1 | RUN/STOP 명령 (읽으면 현재 RUN 여부) | uint16, 0=STOP, 1=RUN | **FC06만** |
| 8 | 1 | TRIP 해제 명령 (읽으면 항상 0) — 6.1절, 2026-11-13 펌웨어 반영 확인 | uint16, 1=해제 | **FC06만** |

### FC10으로 쓸 수 있는 조합

| 시작 | 개수 | 쓰는 항목 |
|---:|---:|---|
| 0 | 7 | 전압 + 전류 + OC + 제한 시간 (**권장**, 바이트 수 14) |
| 0 | 6 | 전압 + 전류 + OC |
| 0 | 4 | 전압 + 전류 |
| 0 | 2 | 전압 |
| 2 | 4 | 전류 + OC |
| 2 | 2 | 전류 |
| 4 | 2 | OC |

권장 방식(시작 0, 개수 7)의 데이터 부분은 `struct.pack('>fffH', voltage, current, oc, seconds)`로 만든다(14바이트).

### 쓰기 규칙 (펌웨어 동작)

- **전부 아니면 전무:** 값 하나라도 범위를 벗어나거나 NaN/Inf면 아무것도 바꾸지 않고 예외 03을 돌려준다.
- **STOP 상태에서만 설정 변경 가능:** RUN 중이거나 DSP의 로컬 메뉴를 쓰는 중이면 예외 04를 돌려준다.
- float의 절반만 쓰기, 홀수 주소에서 시작, FC06으로 float 쓰기, FC10에 RUN/STOP 포함은 모두 예외 02로 거부된다.
- 설정은 RAM에만 반영된다. Flash에 자동 저장되지 않고, 설정만으로 RUN이 시작되지도 않는다.
- **쓰기와 RUN 명령은 자동으로 재시도하지 않는다.** 실패하면 FC03/FC04로 현재 상태를 읽고 판단한다.

## 5. RUN / STOP 절차

1. FC04로 측정값과 상태를 읽고, FC03으로 현재 설정을 읽는다.
2. 상태가 STOP(0)인지 확인한다. TRIP(2)이면 아래 6절을 본다.
3. FC10(시작 0, 개수 7)으로 전압, 전류, OC, 제한 시간을 한 번에 쓴다.
4. FC03으로 다시 읽어 쓴 값이 맞는지 확인한다. float는 정확히 같지 않을 수 있으니 허용 오차로 비교한다.
5. FC06 주소 7에 1을 써서 RUN을 시작한다.
6. RUN 중에는 FC04로 주기적으로 측정값을 읽는다.
7. 끝낼 때는 FC06 주소 7에 0을 써서 STOP한다. 그 뒤 FC04로 STOP 상태를 확인한다.

### RUN이 거부되는 경우 (예외 04)

`app_run()`은 아래 조건을 **모두** 만족할 때만 RUN을 시작한다.
- 상태가 STOP
- 트립 원인이 없음(0)
- 워치독이 운전을 막고 있지 않음
- DSP의 로컬 메뉴나 입력을 쓰는 중이 아님

STOP 명령(값 0)은 상태와 관계없이 항상 받아들인다.

### DSP가 스스로 STOP하는 경우

| 조건 | 결과 |
|---|---|
| 운전 경과 시간이 제한 시간(주소 6) 이상 | STOP |
| **RUN 중 정상 Modbus 요청이 10초 동안 없음** | STOP. 통신이 돌아와도 **자동으로 다시 RUN하지 않음** |
| 출력 전류가 OC 임계값을 넘음 | **TRIP** (트립 원인 3) |

- "정상 요청"은 DSP가 실제로 처리한 FC03, FC04, FC06, FC10 요청이다. CRC 오류, 주소 오류, 형식 오류 프레임은 시간을 연장하지 않는다.
- **RUN 중에는 10초보다 충분히 짧은 주기(예: 1초 이하)로 FC04를 읽어야 한다.** ERS가 긴 작업(ADC 측정, 릴레이 전환)을 하는 동안 이 읽기가 끊기면, ERS가 정지시키지 않았는데도 전원이 꺼진다.

## 6. TRIP 해제 — Modbus로는 불가능

펌웨어에서 TRIP을 해제하는 함수는 `do_reset()` 하나뿐이고, 이 함수는 **DSP 로컬 UART 메뉴의 `e` 키로만** 호출된다.
Modbus에는 TRIP 해제 명령이 없다.

따라서 TRIP이 한 번 나면:
- FC04 상태는 2(TRIP), 트립 원인은 0이 아닌 값으로 남는다.
- FC06 주소 7에 1(RUN)을 써도 예외 04로 거부된다.
- Pi 쪽에서는 복구할 방법이 없다. 사람이 DSP를 직접 리셋하거나 전원을 다시 넣어야 한다.

> **결정 (2026-11-13): 펌웨어에 TRIP 해제 전용 레지스터를 추가한다.** 사양은 6.1절. 같은 날 펌웨어 반영과 기본 동작을 확인했다(11절).
> 펌웨어 수정 요청서: `D:/GPT_Knowledge/ESR_DSP/TRIP_RESET_REGISTER_WORK_ORDER.md` (최대 전류 유지, 부팅 중 거부, 테스트 항목 등 세부 사항 포함)

### 펌웨어에서 확인한 사실 (2026-11-13)

- 실제로 걸리는 TRIP은 **과전류(OC) 하나뿐**이다. 트립 원인 1(TIMER1)과 2(ADC)는 코드로 정의만 돼 있고, 이 값을 설정하는 곳이 없다.
- 과전류가 나면 `check_OC_fast()`가 게이트를 즉시 끄고(GPIO16=1) TRIP 상태로 바꾼다. 해제 시점에는 출력이 이미 차단돼 있다.
- `do_reset()`은 트립 원인을 0으로, 운전 경과 시간을 0으로, 상태를 STOP으로 바꾼다. 설정값(RAM)은 유지하고 RUN하지 않는다.
- 로컬 메뉴의 워치독 리셋(`gu_wdg_inhibit`)으로 DSP를 재부팅해도 TRIP은 풀린다. 하지만 Modbus로 쓴 설정이 사라지고 통신도 잠시 끊겨서, TRIP 해제용으로는 쓰지 않는다.

### 6.1 TRIP 해제 레지스터 사양 (펌웨어 수정 예정)

**레지스터:** 설정 영역(FC03 영역) **주소 8**, `TRIP 해제 명령`, uint16.

| 접근 | 동작 |
|---|---|
| FC06 주소 8 = **1** | TRIP 해제 요청 (아래 표에 따라 처리) |
| FC06 주소 8 = 1이 아닌 값 | 예외 03 |
| FC03으로 읽기 | 항상 0 (명령 전용 레지스터) |
| FC10에 주소 8 포함 | 예외 02 (지금 FC10 규칙 그대로. 시작 0·개수 7을 넘는 요청은 이미 거부됨) |

**상태별 처리:**

| 해제 요청 시 상태 | 응답 | 결과 |
|---|---|---|
| TRIP | 정상 (요청 그대로 되돌려줌) | `do_reset()` 실행 → STOP, 트립 원인 0, 설정 유지, RUN하지 않음 |
| STOP (트립 없음) | 정상 | 아무것도 바꾸지 않음. 같은 요청을 다시 보내도 결과가 같다(멱등) |
| RUN | 예외 04 | 변화 없음 |
| 로컬 메뉴 사용 중 | 예외 04 | 기존 쓰기 규칙과 같음 |
| 출력 전류가 아직 OC 임계값 이상 | 예외 04 | 게이트가 꺼졌는데 전류가 흐르면 하드웨어 이상이다 |

- 해제 요청도 정상 요청이므로, 처리되면 10초 무통신 타이머를 갱신한다(지금 FC06 처리 규칙과 같음).
- 해제하면 트립 원인이 지워진다. **호스트는 해제 전에 FC04를 읽어 트립 원인과 최대 전류를 기록해야 한다.** 펌웨어에 기록용 레지스터는 두지 않는다.
- 해제 후 RUN은 호스트가 FC06 주소 7 = 1로 따로 명령한다.

**예시 프레임:**

| 동작 | 프레임 |
|---|---|
| TRIP 해제 | `01 06 00 08 00 01 C9 C8` |
| 정상 응답 | `01 06 00 08 00 01 C9 C8` |

**펌웨어 수정 범위 (ESR_DSP):**

| 파일 | 수정 |
|---|---|
| `main.c` `app_mb_write()` | 주소 8 처리 추가. 지금은 주소 6, 7 외에는 예외 02 |
| `main.c` `app_mb_read()` | FC03 범위를 8 → 9로, `data[8] = 0` |
| `MODBUS_REGISTER_MAP.md`, `MODBUS_HOST_PROTOCOL.md` | 주소 8 추가, FC03 최대 개수 9 |
| `tests/test_firmware_host.py` | 상태별 처리 표의 각 경우를 테스트로 추가 |
| `modbus_ui/` | 해제 버튼 (선택) |

`modbus_rtu.c`는 수정하지 않아도 된다. FC06은 주소에 관계없이 `app_mb_write()`로 넘어간다.
기존 호스트가 FC03을 시작 0, 개수 8로 읽는 것은 그대로 동작한다.

### 6.2 ERS 쪽 정책

- 과전류 TRIP이 나면 ERS는 **FAULT**로 가고 작업을 멈춘다.
- **ERS는 자동으로 해제하지 않는다.** 같은 조건이면 다시 과전류가 나고, 그때마다 고전압을 다시 인가하게 된다([error-recovery-design.md](error-recovery-design.md)의 무한 반복 문제와 같은 구조).
- 해제는 HOST의 `RESET` 명령으로만 한다. 순서:
  1. FC04로 트립 원인과 최대 전류를 읽어 로그로 남긴다.
  2. FC06 주소 8 = 1을 보낸다.
  3. FC04로 STOP 상태를 확인한다.
  4. READY로 돌아간다.
- 이 `RESET` 명령이 error-recovery-design.md에서 미결로 남은 "FAULT 탈출 경로"가 된다.

## 7. 예외 응답

형식: `[01][기능 코드 | 0x80][예외 코드][CRC 하위][CRC 상위]` (5바이트)

| 코드 | 의미 | DSP에서 발생하는 경우 |
|---:|---|---|
| 01 | 지원하지 않는 기능 | 03, 04, 06, 10 외의 기능 코드 |
| 02 | 잘못된 주소 | 맵 범위 밖, float 절반만 접근, 홀수 시작 주소, FC06으로 float 쓰기, FC10에 주소 7 포함 |
| 03 | 잘못된 값 | 범위 밖 값, NaN/Inf, 개수 0, FC10 바이트 수 불일치 |
| 04 | 현재 상태에서 실행 불가 | RUN 중 설정 쓰기, RUN 조건 미충족, 로컬 메뉴 사용 중 |

개수 제한: FC04 최대 16, FC03 최대 8 (TRIP 해제 레지스터 추가 후 9), FC10 최대 7.

## 10. ERS 2027Version 설계에 반영할 점

1. **통신 계층:** 참조 클라이언트(`modbus_ui/modbus_client.py`)처럼 pyserial로 직접 구현한다. 지켜야 할 것:
   - 8E1로 연다.
   - 요청 사이에 5ms 이상 간격을 둔다.
   - 프레임을 한 번에 쓴다.
   - 100ms 안에 응답이 없으면 실패로 본다.
   - 응답의 CRC, 주소, 기능 코드를 확인한다.
2. **RUN 중 통신 유지:** RUN 동안 FC04 읽기를 끊김 없이 이어가야 한다. 측정이나 릴레이 작업과 별도의 주기 작업(asyncio 태스크 등)으로 돌리는 구조를 검토한다.
3. **오류 분류** ([error-recovery-design.md](error-recovery-design.md)의 기준을 따름):
   - TRIP (과전류) → **FAULT**. 자동 해제하지 않고 HOST `RESET`으로만 해제 (6.2절)
   - Modbus 무응답이 계속됨 → FAULT
   - 예외 04 (상태가 맞지 않음) → 상태를 다시 읽고 판단. 설정과 RUN은 자동으로 재시도하지 않음
4. **설정 적용 순서:** FC10으로 쓰기 → FC03으로 확인 → FC06으로 RUN. 측정 단계마다 전압을 바꿔야 한다면 **매번 STOP → 설정 → RUN**을 거쳐야 한다(RUN 중 설정 변경은 예외 04). 기존 `set_target()`은 목표값을 쓴 뒤 바로 시작하는 구조였으므로, 이 순서에 맞게 다시 설계한다.
5. **전압 범위:** 출력 전압 지령은 1~300V, 전류 지령은 0.1~1A다. 기존의 구간별 BUCK 게인 프로파일(`settings.json`의 `gain_profiles`)은 새 보드에는 필요 없다.
6. **목표 전압 도달 확인:** 새 보드는 "목표 도달" 플래그를 주지 않는다. FC04의 출력 전압을 지령과 비교해 Pi가 판단해야 한다(허용 오차와 대기 시간 정의 필요).
7. ~~장치 없이 개발: 시뮬레이터~~ — 실제 보드를 연결했으므로 만들지 않기로 했다(2026-11-13).

### 10.1 확정한 동작 (2026-11-13 사용자 결정)

| 항목 | 결정 | 설정 키 (`settings.json` `power`) |
|---|---|---|
| 전류 지령 | 잡의 `MaxIval`(mA)을 A로 변환. **1A를 넘으면 1A로 자르고 경고 로그.** 0.1A 미만은 0.1A | `max_current_a` = 1.0, `min_current_a` = 0.1 |
| OC 임계값 | **전류 지령 × 1.5**, 0.3~1.5A 안으로 제한 | `oc_ratio` = 1.5, `oc_min_a` = 0.3, `oc_max_a` = 1.5 |
| 전압 지령 | 1~300V 밖이면 잡 거부 | `min_voltage_v` = 1, `max_voltage_v` = 300 |
| 운전 제한 시간 | **잡 길이로 계산**: 명령 하나당 (ADC 대기 + 릴레이 전환 + 재시도 여유) × 명령 수 × 1.5, 1~9999초 | (ERS_Main에서 계산) |
| 전압 도달 판정 | 출력 전압이 **±1V와 ±2% 중 큰 범위** 안에 들어오면 도달. **2초** 안에 못 들어오면 STOP 후 잡 실패 (기존 보드의 20초에서 단축) | `voltage_tolerance_v`, `voltage_tolerance_pct`, `voltage_settle_timeout_sec` |
| 시험 전압 | 전극 시험(`DoElectrodeTest`)과 ADC 시험(`DoADCTest`)은 **30V 고정** (기존 동작 유지) | `test_voltage_v` = 30 |
| RUN 중 통신 유지 | 별도 스레드가 1초마다 FC04를 읽음. 연속 3회 실패하면 통신 두절 | `keepalive_interval_sec` = 1.0, `keepalive_fail_limit` = 3 |
| 부스터 | **새 하드웨어에 없음.** 부스터 제어 코드를 제거 | — |

- 1A, 1.5A 상한은 지금 펌웨어 기준이다. **하드웨어 정격을 확인한 뒤 조정한다**(펌웨어 범위도 함께 바꿔야 함).
- 2026-11-13 확인: 전류 지령 2.0A는 DSP가 예외 03으로 거부한다.

## 11. 실제 통신 기록

### 2026-11-13 첫 연결 — 읽기만

`DeviceTest/dsp_modbus_test.py read`. 첫 시도에 두 요청 모두 정상 응답, CRC 오류 없음.

```
TX 01 04 00 00 00 10 F1 C6
RX 01 04 20 C1 CF ED E9 C1 D0 B2 1E 3D EE 8E E9 00 00 00 00 00 00 00 00 41 3D DA 5D 41 3E D9 78 00 00 00 00 39 7D
   상태 STOP, 트립 없음, 경과 0s
   입력 -25.991V  출력 -26.087V  0.1165A  peak 0  VBAT 11.866V  P12V 11.928V

TX 01 03 00 00 00 08 44 0C
RX 01 03 10 3F 80 00 00 3D CC CC CD 3F C0 00 00 00 0A 00 00 35 D5
   지령 1.0V  0.1A  OC 1.5A  제한 10s  RUN=0
```

- 9600bps, 8E1, 주소 1, float32 ABCD 순서가 문서대로 동작함을 확인했다.
- **입력·출력 전압이 -26V 근처의 음수, STOP 중 출력 전류 0.12A**로 읽힌다. 통신 문제가 아니라 DSP가 계산한 값이다. 센서 오프셋 또는 보정 문제로 추정되며 확인이 필요하다(당시 입력 전원 상태는 미확인).
- 설정값(1V, 0.1A, 1.5A, 10s)은 DSP Flash 기본값으로 보인다.

### 2026-11-13 TRIP 해제 레지스터(주소 8) 시험 — STOP 상태에서

펌웨어에 해제 레지스터가 반영된 것을 확인했다. 모두 상태를 바꾸지 않는 요청이며, 시험 전후 상태와 설정은 같았다.

| 요청 | 프레임 | 응답 | 사양과 비교 |
|---|---|---|---|
| 해제 (STOP, 트립 없음) | `01 06 00 08 00 01 C9 C8` | `01 06 00 08 00 01 C9 C8` 정상 | 맞음 (STOP에서는 아무것도 바꾸지 않음) |
| FC03 시작 0, 개수 9 | `01 03 00 00 00 09 85 CC` | 18바이트, 주소 8 = 0 | 맞음 |
| FC06 주소 8 = 0 | `01 06 00 08 00 00 08 08` | `01 86 03` 예외 03 | 맞음 |
| FC06 주소 8 = 2 | `01 06 00 08 00 02 89 C9` | `01 86 03` 예외 03 | 맞음 |
| FC03 시작 0, 개수 10 | `01 03 00 00 00 0A C5 CD` | `01 83 02` 예외 02 | 맞음 |

### 2026-11-13 RUN/STOP 시퀀스 시험 — 17/17 통과

당시 DSP 보드는 전압을 출력하지 못하는 상태여서(사용자 확인) RUN을 자유롭게 시험했다.
시험 후 설정을 원래 값(1V, 0.1A, OC 1.5A, 10s)으로 되돌렸다.

| 시험 | 결과 |
|---|---|
| FC10 설정 쓰기(5V, 0.2A, OC 0.5A, 5s) 후 FC03으로 확인 | 통과 |
| FC06 RUN → FC04 상태 1, FC03 RUN 플래그 1 | 통과 |
| RUN 중 TRIP 해제 / FC10 설정 / FC06 제한 시간 쓰기 → 모두 예외 04, 설정 변화 없음 | 통과 |
| 제한 시간 5s 후 자동 STOP (실측 약 5.6s, 0.5s 간격 폴링), RUN 플래그 0 | 통과 |
| RUN 중 12초 동안 요청 없음 → STOP, 경과 10s에서 멈춤. 통신 재개 후 자동 RUN 없음 | 통과 |
| RUN 중 FC06 STOP → 즉시 STOP. STOP 중 STOP 재전송 허용 | 통과 |
| STOP 중 TRIP 해제 → 정상 응답, 상태 변화 없음 | 통과 |

- RUN 중에도 출력 전압은 -26V(미캘리브레이션 값) 그대로였다. 보드가 출력하지 못하는 상태와 일치한다.
- 최대 전류(peak)는 RUN 진입 때 0으로 초기화된 뒤 RUN 중 0.1179A까지 기록됐다(오프셋 값).

**아직 시험하지 않은 것:** 실제 TRIP 상태에서 STOP으로 풀리는지, 트립 직후 전류가 남아 있을 때 해제가 거부되는지.
OC 임계값의 최솟값(0.3A)보다 큰 전류가 실제로 흘러야 TRIP이 걸리므로, 출력이 되는 보드와 부하가 필요하다.

## 12. 미확인 / 확인할 것

- `MODBUS_HOST_PROTOCOL.md`의 한글 원문 복구. 펌웨어 담당에게 원본을 다시 받아야 한다.
- DSP 부팅 후 Modbus 응답을 받을 수 있을 때까지 걸리는 시간.
- 출력 전압이 지령에 도달하는 데 걸리는 시간과 정착 오차 (실측 필요).
- 전류 지령 0.1~1A의 실제 의미: 정전류 제한인지, 목표 전류인지.
- RUN 중 Pi가 STOP을 보낸 뒤 출력이 실제로 0V까지 떨어지는 시간 (방전, `EPWM2` 방전 듀티 관련).
- 9600bps에서 FC04 한 번 왕복에 약 50ms가 걸린다. ERS 측정 시퀀스의 시간 예산 안에 들어가는지 확인.
